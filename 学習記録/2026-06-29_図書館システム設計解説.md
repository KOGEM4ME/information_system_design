## Step 1：問題の整理（要求定義）

README の「現状の課題」から出発する。

```
- 利用者が貸出状況をリアルタイムで確認できない
- 手作業のため延滞管理に時間がかかる
- 貸出中の本を予約できる仕組みがない
```

**「誰が何をしたいのか」を整理する（ステークホルダの識別）**

```
利用者  → 本を探したい・在庫を知りたい
職員   → 貸出・返却を登録したい・延滞者を把握したい
管理者 → 蔵書・利用者を登録・削除したい
```

この「誰が何をするか」がそのまま画面の一覧になる。

```
利用者用  → search.html（蔵書検索）
職員用   → loan.html / return.html / overdue.html
管理者用  → admin_books.html / admin_members.html
```

**考え方：画面の数 ＝ ユーザーがやりたいことの数**

## Step 2：データの整理（DB設計）

「このシステムで扱うデータは何か」を考える。

現実の図書館業務を観察すると：

- 本がある → **BOOKSテーブル**
- 人がいる → **MEMBERSテーブル**
- 人が本を借りる → **LOANSテーブル**（BOOKSとMEMBERSをつなぐ）

```python
# database.py の設計

BOOKS:   book_id, title, author, isbn, category, total_copies, available_copies
MEMBERS: member_id, name, email, registered_at
LOANS:   loan_id, book_id, member_id, loaned_at, due_date, returned_at
```

**なぜ `returned_at` を NULL にするのか？**

返却済みかどうかを「別のフラグ列」で管理するより、
「返却日時がなければ貸出中」の方がシンプル。

```sql
WHERE returned_at IS NULL  -- 未返却 = 貸出中の判定
```

## Step 3：3層アーキテクチャへの分割

```
database.py  → データ層：DBの作成・接続
models.py    → アプリ層：ビジネスロジック（貸出ルールの判定など）
app.py       → プレゼン層：URLの受け取り・画面の表示
templates/   → プレゼン層：HTMLの見た目
```

**なぜ分けるか（models.py の loan_book() の例）**

```python
def loan_book(book_id, member_id):
    # ① 在庫確認
    if book["available_copies"] <= 0:
        return False, "この本は現在貸出できません"

    # ② 上限確認（ビジネスルール：同時5冊まで）
    if cursor.fetchone()[0] >= 5:
        return False, "貸出上限（5冊）に達しています"

    # ③ 延滞確認（7日以上延滞で停止）
    if cursor.fetchone()[0] > 0:
        return False, "延滞中のため貸出できません"

    # ④ すべてOKなら登録
    due_date = 今日 + 14日
```

この「①②③の順でチェックする」がビジネスロジック。
これが app.py に混ざると、URLの処理とルールの処理が混在して読みにくくなる。

app.py はただ呼び出すだけでよい：

```python
@app.route("/loan", methods=["POST"])
def loan():
    success, message = models.loan_book(book_id, member_id)  # 1行で済む
    flash(message)
    return redirect(url_for("loan"))
```

**考え方：「何をするか（ロジック）」と「どう見せるか（画面）」は別の関心事**

## Step 5：実装で工夫した点

### ① GETとPOSTの使い分け

```python
@app.route("/loan", methods=["GET", "POST"])
def loan():
    if request.method == "POST":
        # フォーム送信 → 処理する
    # GET → フォームを表示するだけ
```

- GET：「見る」操作（URLに条件が入るので共有できる）
- POST：「変更する」操作（データを変更するので）

### ② PRGパターン（二重送信の防止）

```python
# 処理後はリダイレクト（再読み込みで二重送信されない）
return redirect(url_for("loan"))
```

ブラウザの「戻る」「再読み込み」で同じ貸出が2回登録されないための工夫。

### ③ テンプレート継承

```html
<!-- base.html：全ページ共通のナビバー・CSSを1か所に書く -->
<!-- 各ページは block content の中だけ書けばいい -->
{% extends "base.html" %}
{% block content %}
  <!-- このページ固有の内容だけ -->
{% endblock %}
```

ナビバーを6ページ分コピペするのではなく、1か所だけ書けば全ページに反映される。
