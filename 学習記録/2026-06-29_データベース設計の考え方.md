## Step 1：なぜデータベースが必要か

Python のリストで管理した場合の問題点：
- プログラムを終了するとデータが消える
- 複数人が同時にアクセスすると壊れる
- 特定データの検索が遅い

→ SQLite（`library.db`）で永続化・高速検索・同時アクセスを解決

---

## Step 2：テーブルをどう分けるか（正規化）

### 悪い例（1テーブルに全部詰め込む）

```
┌──────────┬──────┬──────────┬──────────┐
│ 書名      │ 著者 │ 利用者名 │ 返却期限 │
├──────────┼──────┼──────────┼──────────┤
│ Python入門│Guido │ 山田太郎 │2026-07-13│
│ Python入門│Guido │ 鈴木花子 │2026-07-20│  ← 同じ本の情報が重複
└──────────┴──────┴──────────┴──────────┘
```

**3つの異常が発生する：**
- 更新異常：著者名変更時に全行変更が必要
- 削除異常：貸出削除で本の情報も消える
- 挿入異常：誰も借りていない本を登録できない

### 正規化後（テーブルを分割）

```
BOOKS（本の情報）  MEMBERS（人の情報）  LOANS（借りた記録）
book_id で識別     member_id で識別     book_id と member_id を FK で参照
```

**正規化の原則：繰り返す情報を別テーブルに切り出す**

---

## Step 3：主キーと外部キーの役割

```python
# database.py より

# 主キー（PK）：その行を一意に識別する番号（自動採番）
book_id INTEGER PRIMARY KEY AUTOINCREMENT

# 外部キー（FK）：他テーブルの主キーを参照
FOREIGN KEY (book_id)   REFERENCES BOOKS(book_id)
FOREIGN KEY (member_id) REFERENCES MEMBERS(member_id)
```

**なぜ名前ではなく番号（ID）で参照するか？**
→ 名前が変わっても ID を変えなければ貸出記録は壊れない。
  名前で参照していたら全 LOANS を書き換える必要がある。

**FK の効果（models.py の JOIN）：**
```python
SELECT m.name, b.title, l.due_date
FROM LOANS l
JOIN MEMBERS m ON l.member_id = m.member_id
JOIN BOOKS   b ON l.book_id   = b.book_id
```

## Step 4：available_copies の設計判断（意図的な非正規化）

### 計算で求める方法（正規化的）

```sql
SELECT total_copies - COUNT(*)
FROM BOOKS LEFT JOIN LOANS ON ...
WHERE LOANS.returned_at IS NULL
-- 本が増えるほど検索のたびに重くなる
```

### 今回の方法（非正規化）

```python
# BOOKS テーブルに available_copies 列を持たせる
# 貸出・返却のたびに更新する

# 貸出時
UPDATE BOOKS SET available_copies = available_copies - 1

# 返却時
UPDATE BOOKS SET available_copies = available_copies + 1
```

**非正規化とは：**
正規化の原則をあえて破って、検索速度を優先する設計判断。
「速度」と「データの一貫性」のトレードオフ。

## Step 5：returned_at を NULL にする設計

```python
# フラグ列を使う方法（冗長）
is_returned BOOLEAN  # True/False
returned_at TEXT     # 返却日時 → 2列で同じ情報を管理

# 今回の方法（シンプル）
returned_at TEXT     # NULL = 貸出中 / 日時あり = 返却済み
```

```python
# models.py
WHERE returned_at IS NULL  # = 今も貸出中
```

**1列で「状態」と「日時」の両方を表現できる。**

## まとめ：DB設計の思考の流れ

```
① 扱うデータを洗い出す
  「本がある」「人がいる」「人が本を借りる」
        ↓
② 1テーブルに全部入れてみる
  → 重複・異常が起きることを確認
        ↓
③ 繰り返す情報を別テーブルに切り出す（正規化）
  BOOKS / MEMBERS / LOANS / RESERVATIONS
        ↓
④ テーブル間の関係をIDで表す（FK設計）
  LOANS は book_id と member_id だけ持つ
        ↓
⑤ パフォーマンスのために意図的に非正規化する
  available_copies を BOOKS テーブルに持たせる
        ↓
⑥ NULL の意味を設計する
  returned_at IS NULL = 貸出中
```
