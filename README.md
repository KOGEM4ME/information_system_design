## 1. 概要

### 1.1 システム化の目的

本システムは、大学図書館における蔵書管理業務を情報システム化し、利用者の利便性向上と職員の業務効率化を実現することを目的とする。

現在の図書館では、利用者が蔵書を探す際に目録カードや館内端末を利用しているが、貸出状況をリアルタイムで確認する手段がなく、不便が生じている。また、職員は貸出・返却管理を手作業で行っており、延滞管理に多くの時間を要している。

### 1.2 現状の課題

- 利用者が蔵書の貸出状況をリアルタイムで確認できない
- 複数条件（書名・著者・分類）を組み合わせた蔵書検索が困難
- 貸出・返却処理が手作業のため、延滞管理に時間がかかる
- 貸出中の本を他の利用者が予約できる仕組みがない
- 職員が手作業で延滞者リストを作成しており、ミスが発生しやすい

### 1.3 システム構成図（3層アーキテクチャ）

本システムは授業で学んだ3層アーキテクチャに基づき設計する。

| 層 | 役割 | 主な構成要素 |
|---|---|---|
| プレゼンテーション層 | ユーザインタフェースの提供 | 蔵書検索画面 / 貸出・返却画面 / 管理画面 |
| アプリケーション層 | 業務ロジックの処理 | 検索処理 / 貸出管理 / 延滞チェック / 予約処理 |
| データ層 | データの管理・永続化 | 蔵書DB / 利用者DB / 貸出DB / 予約DB |

### 1.4 用語定義

| 用語 | 定義 |
|---|---|
| 蔵書 | 図書館が所蔵する書籍・資料の総称 |
| 貸出 | 利用者が蔵書を一定期間借り出すこと（貸出期間：2週間） |
| 返却 | 貸出中の蔵書を図書館に戻すこと |
| 予約 | 貸出中の蔵書に対して返却後の貸出権を確保すること |
| 延滞 | 返却期限を過ぎても返却されていない状態 |
| 利用者 | 図書館に登録された学生・教職員 |
| 職員 | 図書館の窓口業務を担当するスタッフ |

## 2. ステークホルダの識別

本システムに利害関係を持つステークホルダを以下のとおり識別した。

| ステークホルダ | 役割 | 主な関心事 |
|---|---|---|
| 利用者（学生・教職員） | 蔵書の検索・貸出・返却・予約を行う | 探している本をすぐに見つけられるか、貸出状況をリアルタイムで知れるか |
| 図書館職員 | 貸出・返却登録、延滞管理を行う | 業務の効率化、延滞管理の自動化 |
| 図書館管理者 | システム全体の管理・蔵書登録を行う | 蔵書データの正確性、利用統計の把握 |
| 大学情報システム部門 | システムの運用・保守を担当する | システムの安定稼働、セキュリティ |

## 3. 機能要求（Functional Requirements）

### 3.1 蔵書検索機能

| ID | 要求内容 | 優先度 |
|---|---|---|
| FR-01 | 利用者は書名・著者名・キーワードで蔵書を検索できる | 高 |
| FR-02 | 検索結果に貸出状況（在庫あり／貸出中／予約中）をリアルタイムで表示する | 高 |
| FR-03 | 複数条件（AND検索）を組み合わせた絞り込みができる | 中 |
| FR-04 | 検索結果をカテゴリ・著者・出版年で並び替えられる | 低 |

### 3.2 貸出・返却機能

| ID | 要求内容 | 優先度 |
|---|---|---|
| FR-05 | 職員は利用者IDと蔵書IDを入力して貸出登録できる | 高 |
| FR-06 | 職員は蔵書IDを入力して返却登録できる | 高 |
| FR-07 | 貸出時に自動的に返却期限（貸出日から14日後）を設定する | 高 |
| FR-08 | 貸出・返却ともに登録完了後、確認票を発行できる | 中 |

### 3.3 予約機能

| ID | 要求内容 | 優先度 |
|---|---|---|
| FR-09 | 利用者は貸出中の蔵書を予約できる | 中 |
| FR-10 | 予約蔵書が返却されたとき、予約者にメールで通知する | 中 |
| FR-11 | 利用者は自身の予約状況を確認・キャンセルできる | 低 |

### 3.4 延滞管理機能

| ID | 要求内容 | 優先度 |
|---|---|---|
| FR-12 | 職員は延滞者の一覧（利用者名・蔵書名・延滞日数）を確認できる | 高 |
| FR-13 | 返却期限の3日前に利用者へリマインドメールを自動送信する | 中 |
| FR-14 | 延滞者には次の貸出を制限できる | 低 |

### 3.5 蔵書管理機能（管理者）

| ID | 要求内容 | 優先度 |
|---|---|---|
| FR-15 | 管理者は蔵書（書名・著者・ISBN・冊数等）を登録・編集・削除できる | 高 |
| FR-16 | 管理者は利用者を登録・編集・削除できる | 高 |
| FR-17 | 管理者は貸出件数・利用者数などの統計情報を確認できる | 低 |

ISO/IEC 25010の品質特性に基づき、非機能要求を定義する。

| ID | 要求内容 |
|---|---|
| NFR-01 | 蔵書検索の結果は3秒以内に表示される |

### 4.2 使用性

| ID | 要求内容 |

## 5. 業務要求

### 5.1 貸出業務フロー（概要）

1. 利用者が蔵書を検索し、在庫があることを確認する
2. 利用者が窓口に来館し、職員に貸出を申請する
3. 職員が利用者IDと蔵書IDを入力し、貸出登録を行う
4. システムが返却期限を自動設定し、確認票を発行する

### 5.2 返却業務フロー（概要）

1. 利用者が蔵書を窓口に返却する
2. 職員が蔵書IDを入力し、返却登録を行う
3. 予約者がいる場合、システムが自動でメール通知を送信する

### 5.3 ビジネスルール

| ルール | 内容 |
|---|---|
| 貸出期間 | 貸出日から14日間（延長は職員が対応） |
| 貸出冊数上限 | 1人につき同時5冊まで |
| 予約上限 | 1人につき同時3件まで |
| 延滞制限 | 返却期限から7日以上経過した場合、次の貸出を停止 |

## 6. データベース設計（概要）

第8回で学んだ正規化の考え方に基づき、4つのテーブルを設計する。

### 6.1 テーブル一覧

| テーブル名 | 説明 | 主なカラム |
|---|---|---|
| BOOKS（蔵書） | 蔵書の基本情報を管理する | book_id (PK), isbn, title, author, category, total_copies, available_copies |
| MEMBERS（利用者） | 登録利用者の情報を管理する | member_id (PK), name, email, registered_at |
| LOANS（貸出） | 貸出・返却の記録を管理する | loan_id (PK), book_id (FK), member_id (FK), loaned_at, due_date, returned_at |
| RESERVATIONS（予約） | 予約情報を管理する | reservation_id (PK), book_id (FK), member_id (FK), reserved_at |

### 6.2 主なリレーション

- `BOOKS : LOANS` = 1 : 多（1冊の本に複数の貸出記録）
- `MEMBERS : LOANS` = 1 : 多（1人が複数回借りる）
- `BOOKS : RESERVATIONS` = 1 : 多（1冊の本に複数の予約）
- `MEMBERS : RESERVATIONS` = 1 : 多（1人が複数予約）

## 7. 要求の優先順位付け

コストと開発期間の制約から、MoSCoW法で優先度を設定する。

| 優先度 | 意味 | 対象機能 |
|---|---|---|
| Must（必須） | 必ず実装する | 蔵書検索（FR-01, 02）/ 貸出・返却（FR-05, 06, 07）/ 蔵書・利用者登録（FR-15, 16）/ 延滞一覧（FR-12） |
| Should（重要） | できる限り実装する | 複合検索（FR-03）/ 確認票発行（FR-08）/ 予約（FR-09, 10）/ リマインドメール（FR-13） |
| Could（あれば良い） | 余裕があれば実装する | 並び替え（FR-04）/ 予約管理（FR-11）/ 延滞制限（FR-14）/ 統計（FR-17） |
| Won't（今回は対象外） | 今回のスコープ外 | モバイルアプリ対応、他システム連携 |

## 8. 開発方針

### 8.1 採用するライフサイクルモデル

**インクリメンタルモデル**を採用する。

採用理由：

- 基本機能（検索・貸出・返却）と拡張機能（予約・統計）の分離が明確であるため
- 基本機能を早期にリリースし、フィードバックを得ながら機能追加できるため
- 開発期間が限られており、段階的にリリースすることでリスクを低減できるため

| フェーズ | 実装内容 | 期間 |
|---|---|---|
| フェーズ1 | 蔵書検索・貸出・返却の基本機能（Must要件） | 第12〜13回実習 |
| フェーズ2 | 予約・延滞管理・リマインド機能（Should要件） | 第14回プレゼン前 |
| フェーズ3 | 統計機能・UI改善（Could要件） | 余裕があれば |

### 8.2 技術スタック

| 項目 | 採用技術 | 理由 |
|---|---|---|
| 言語 | Python | 授業での使用経験があり、チーム全員が扱える |
| Webフレームワーク | Flask | 軽量でシンプル、小規模開発に適している |
| データベース | SQLite | 追加インストール不要、開発・テストが容易 |
| フロントエンド | HTML / CSS / JavaScript | 標準技術で汎用性が高い |

### 8.3 開発メンバーと役割

| 名前 | 役割 |
|---|---|
| | プロジェクトリーダー / 要求定義 |
| | バックエンド実装 / DB設計 |
| | フロントエンド実装 / UIデザイン |
| | テスト / ドキュメント |
